## Autonomous Module Integration Plan

### Architecture
The SPCS orchestration service has no network ingress. All communication happens through **3 Snowflake stored procedures** called via the Snowflake SQL API (`POST /api/v2/statements`) using the existing PAT (`SNOWFLAKE_TOKEN` in `.env`).

### Implementation Steps

#### 1. Snowflake SQL API helper (`frontend/lib/snowflake-api.ts`)
- Create a server-side utility that calls `POST https://{account}.snowflakecomputing.com/api/v2/statements` with Bearer PAT auth
- Handle async statement execution (poll for results via statement handle)
- Parse VARIANT column results from the 3 procedures

#### 2. Next.js API routes for orchestration (3 routes)
- **`POST /api/autonomous/submit`** — calls `SUBMIT_ORCHESTRATION(NULL, 'autonomous', personas)`, returns `run_id`
- **`GET /api/autonomous/events?run_id=X`** — calls `GET_ORCHESTRATION_EVENTS(run_id)`, returns node status rows
- **`GET /api/autonomous/result?run_id=X`** — calls `GET_ORCHESTRATION_RESULT(run_id)`, returns the full payload

#### 3. Update global personas (`frontend/lib/constants.ts`)
- Replace the single "Demand Analyst" persona with the orchestrator-compatible set: "Director of Demand Planning", "Supply Chain Director" (and any others the backend supports)
- Update `MODULE_BULLETS` accordingly

#### 4. Update AppContext for new orchestration model (`frontend/context/AppContext.tsx`)
- Replace the old pipeline state types (`PipelineResult`, `ScorecardData`) with types derived from the real orchestration payloads (exec_report shape, node events shape)
- Add `runId` state, node status map, polling control

#### 5. TypeScript types for orchestration payloads (`frontend/lib/orchestration-types.ts`)
- Types for: `OrchestrationResult` (exec_report, result, status, etc.), `OrchestrationEvent` (NODE_NAME, STATUS, WAVE_NO, etc.), `ExecReport` (enterprise_summary, sections[], validation_summary, pending_approvals), `Section` (persona, key_metrics, anomalies, drivers, risks, recommended_actions, trajectory, caveats)
- Derived defensively from the actual `run-899c53188864` payload — no hardcoded assumptions

#### 6. Autonomous page (`frontend/app/autonomous/page.tsx`)
**Three states: Idle → Running → Report**

**Idle state:**
- Persona multi-select (checkboxes for available personas)
- "Run Pipeline" button

**Running state — Live Agent Network Visualization:**
- Hardcoded topology (per handoff): wave 0 → wave 1 → wave 2 (4 parallel) → wave2_join → prescriptive → validation_gate → wave 5
- Poll `GET_ORCHESTRATION_EVENTS` every 2-3s
- Color nodes by status: running (pulse), ok (green), error (red), timeout (orange), degraded (yellow)
- Show agent name, duration, wave number
- validation_gate rendered as a gate (not another parallel step)
- wave2_join omitted or implicit

**Completed state — Executive Briefing Report (payload-driven):**
- **Enterprise Summary header**: anomalies_total, anomalies_high_impact, departments_affected, net_revenue_at_stake_usd, protected_recovered_usd, total_action_cost_usd, decisions stats
- **Per-persona sections** (loop over `sections[]`): headline, key_metrics cards, anomalies table, drivers table, risks list, recommended_actions with approval badges, trajectory data, caveats (always shown — trust surface)
- **Pending approvals** section
- **Validation summary**: verdict badge + caveats
- **Cross-department contentions** if present

**Edge cases (required by handoff):**
- DATA GAP headlines → render as honest empty state with headline shown
- exec_report NULL + status COMPLETED → fall back to `result.narrative`
- FAILED → short error message, log full traceback, no raw traceback shown
- Individual node error/timeout/degraded → distinct colors, run still continues

#### 7. Update `frontend/lib/api.ts`
- Add methods: `submitOrchestration(personas)`, `getOrchestrationEvents(runId)`, `getOrchestrationResult(runId)`
- Remove or keep old autonomous methods (they're dead code from the old Flask backend)

#### 8. Remove old autonomous API route stubs
